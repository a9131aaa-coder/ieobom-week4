입어봄 · PRD v1

AI와 창업혁신 / 4주차: PRD에서 첫 배포까지 버전 0.1.0 · 작성일 2026-10-16 · 단계: 대시보드 + mock API 브랜드명은 기존 발표자료의 가칭 ‘입어봄’을 유지한다. 신규 이름은 확정하지 않는다.

이번 버전 한 문장

내 옷과 취향을 활용하는 AI 코디 컨설턴트의 홈 대시보드에서, 남은 상담 횟수·등록한 옷·취향 프로필과 최근 코디 상담을 확인한다. 이번 주에는 실제 AI 상담을 수행하지 않는다.

1. 목적

사용자가 접속하자마자 상담 이용 현황, 등록한 의류 수, 프로필 완성도와 이전 코디 기록을 확인하도록 한다. 이번 과제의 목표는 전체 서비스를 완성하는 것이 아니라, 화면이 실제 API의 예시 데이터를 받아 표시하는 구조를 만들고 공개 URL로 접근하게 하는 것이다.

제품의 장기 가치 제안은 ‘매번 취향을 다시 설명하지 않고 내 옷으로 다음 코디 선택을 돕는다’이다. 추천 품질·수요·결제 의사는 미검증이다.

2. 사용자

타깃 가설: 출근·약속에 단정하게 입고 싶지만 편안함을 포기하고 싶지 않고, 가진 옷으로 조합을 정하기 어려운 여성 사회초년생.

비타깃: 새 옷 쇼핑만 원하거나, 실시간 인간 스타일리스트 상담·정밀한 사이즈 판정·가상 피팅을 원하는 사람.

이번 화면은 누구나 열 수 있는 수업용 데모이며 실제 개인 계정이나 고객 기록을 사용하지 않는다. 데이터의 인물·활동·수치는 모두 가상이다.

3. 화면

전체 서비스의 화면 후보는 최대 다섯 개다. 현재 구현은 홈 대시보드 한 개뿐이다.

화면역할4주차 상태
홈 대시보드숫자 카드 3개와 최근 코디 상담 목록 1개구현
내 옷장보유 의류 등록·관리메뉴명만 표시, 비활성
코디 상담사진·상황 입력, 수정안 확인메뉴명만 표시, 비활성
착용 기록실제 착용과 피드백 기록메뉴명만 표시, 비활성
스타일 프로필선호·비선호·편안함 조건 관리메뉴명만 표시, 비활성

홈 대시보드 구성

  • 카드 1: 이번 달 남은 상담 — summary.remaining / summary.limit
  • 카드 2: 등록한 옷 — summary.wardrobeCount
  • 카드 3: 취향 프로필 — summary.profileCompletion%
  • 목록 1개: 최근 코디 상담 5건 — 코디 제목·간단 설명·상황·날짜·상태
  • 남은 상담 진행률은 remaining / limit × 100으로 계산한다. 한도가 0이면 0%다.
  • 다시 불러오기 버튼으로 API를 재요청한다. 로딩과 실패 상태를 구분한다.
  • 데스크톱은 사이드 메뉴, 모바일은 상단 메뉴로 배치한다. 4개 미구현 메뉴는 클릭할 수 없다.
  • 헤더와 하단에 수업용·예시 데이터임을 명시한다. 실제 서비스 성과로 오인시키지 않는다.

화이트·블랙 중심의 편집디자인, 얇은 구분선, 넓은 여백을 사용한다. Pretendard를 외부 CSS로 참조하고, 불러오지 못하면 시스템 한글 고딕으로 대체한다. 글꼴 파일은 배포 ZIP에 포함하지 않는다.

4. 데이터

지금 사용하는 데이터

data/dashboard.json이 유일한 원본이다. lib/dashboard-data.mjs의 getDashboard()가 읽고 검증하며 GET /api/dashboard가 그대로 JSON으로 반환한다. 예시 숫자를 화면 코드에 적지 않는다.

항목예시 / 의미
modemock — 수업용 예시 데이터
periodLabel2026년 10월 · 예시
summary.remaining17 — 남은 상담 횟수 가정
summary.limit20 — 월 한도 가정

날짜·상태·사용량은 샘플이다. 상태는 ‘착용 완료’, ‘피드백 대기’, ‘저장됨’을 사용한다. 이 값으로 실제 AI 분석, 프로필 진단 또는 결제가 이뤄졌다고 주장하지 않는다.

썸네일은 이전 과제용 AI 포스터의 의류 이미지를 잘라 사용한 시각적 예시다. 실제 사용자가 등록한 사진이 아니며, 개별 상담의 실제 결과를 증명하지 않는다.

후속 데이터 구조 초안 — 아직 구현하지 않음

최대 7개 테이블 후보: users(취향 프로필 포함), wardrobe_items, consultations, feedback, weekly_plans, usage_logs, subscriptions. 실제 스키마·권한·개인정보 처리·과금 로직은 해당 수업에서 확정한다. Supabase 내부 인증 테이블의 산정 방식은 교수님 확인이 필요하다.

5. API와 기술 구성

  • 프로젝트: Next.js App Router + TypeScript. 스타일은 별도 CSS로 구현한다.
  • API: GET /api/dashboard 1개. 성공은 200 + JSON, 파일 읽기·검증 실패는 500 + 오류 JSON.
  • 이번 주 데이터 외부 API: 0개. AI·결제·날씨 API, 환경변수, 비밀 키를 사용하지 않는다.
  • Pretendard 외부 스타일시트는 폰트 표시를 위한 참조이며 데이터 API가 아니다. 실패 시 기능에는 영향을 주지 않는다.
  • Vercel 배포 시 data/dashboard.json을 서버 함수에 포함하도록 파일 추적 설정을 둔다.
  • 차후 AI API는 서버에서만 호출한다. 키를 브라우저 코드나 GitHub에 넣지 않는다.
  • 제출용 public/PRD.html은 이 설계서를 공개하는 정적 문서다. 별도 서비스 기능 화면이 아니다.

수업 예시는 Tailwind를 사용하지만, 이 구현은 동일한 디자인 규칙을 public/dashboard.css의 CSS 변수에 모아 작성했다. 기본 스택인 Next.js + Vercel과 API 데이터 흐름은 유지한다.

6. 사용·요청 흐름

  1. 브라우저가 배포 사이트의 /에 접속한다.
  2. Next.js의 app/page.tsx가 고정 화면 구조를 제공한다.
  3. public/dashboard.mjs가 GET /api/dashboard를 요청한다.
  4. app/api/dashboard/route.ts가 getDashboard()를 호출한다.
  5. 함수가 mock JSON을 읽고 유효성을 확인한다.
  6. API의 JSON 응답으로 카드 숫자·진행률·목록 5건을 채운다.
  7. 다시 불러오기를 누르면 같은 API를 재요청한다.

실패 시 이전 숫자를 성공처럼 남기지 않고 ‘—’와 오류 안내를 표시한다. 12초 안에 응답이 오지 않으면 재시도를 안내한다. 데이터 문구는 textContent로 넣어 HTML 실행을 방지한다.

7. 제외 범위

이번 버전에는 로그인·회원가입·실제 DB 저장·사진 업로드·AI 분석·이미지 생성·가상 피팅·결제·실시간 날씨·쇼핑몰 연동·자동 스케줄 실행을 넣지 않는다. 내 옷장 등 다른 메뉴는 이름만 표시한다.

차트, 검색창, 알림 센터, 별도의 가입 유도 페이지도 만들지 않는다. 현재 사이트는 개인 정보를 받지 않는 공개 데모다. 수치와 기록을 사용자별 실데이터처럼 표현하지 않는다.

8. 완료 기준

  • □ 제출용 Vercel URL이 로그인 없이 다른 기기에서 열린다.
  • □ 본문에 숫자 카드가 정확히 3개이고 최근 상담 목록이 1개, 데이터 행이 5개다.
  • □ 브라우저 Network 탭에서 /api/dashboard GET의 상태 200을 확인한다.
  • □ 카드 숫자와 기록이 data/dashboard.json에서 온다. 화면 코드에는 값이 없다.
  • □ JSON의 수치를 변경하면 재배포 후 화면에도 반영된다.
  • □ 로딩·네트워크 오류·재시도 상태가 정상적으로 표시된다.
  • □ 모바일에서 가로 넘침 없이 읽히고, 미구현 메뉴는 비활성이다.
  • □ 한국어가 깨지지 않고 예시 데이터라는 안내가 보인다.
  • □ npm run build가 성공한다.
  • □ PRD 문서 링크, Network 캡처, 본인의 한 줄 회고를 준비한다.

체크박스는 최종 배포 환경에서 확인하고 체크한다. 개발 환경의 시각·단위 테스트 결과와 실제 공개 배포의 성공은 구분한다.
